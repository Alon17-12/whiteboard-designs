מערך הידע — מרכז עזרה שמתעדכן מהמערכת החיה

מרכז עזרה ציבורי (help.whiteboard.education) לשני קהלים — מרצים ותלמידים — שבו כל צילום מסך הוא תוצר של "מתכון" הניתן להרצה מחדש מול הפרודקשיין, וסוכן סורק תקופתי מזהה פיצ'רים חדשים, מסכים שהשתנו ומתכונים שנשברו. כולל תשתית "דברו עם נציג" — פניות תמיכה עם חיבור ל-Admin CRM ומיילים אוטומטיים (סעיף 10). גרסה 1.3 · יולי 2026 · אלון גבאי.

00סקירה + כללי CTO

86 מאמרים (מרצה: 13 קטגוריות · תלמיד: 5, אזור מבודד לחלוטין) · 180 מתכוני צילום · אתר סטטי בעיצוב מערכת WHITEBOARD (light+dark, RTL, Fredoka/Heebo) · צ'אט בורדי שמנווט את הקורא למדריך · תגי מסלולים אוטומטיים · טופס "דברו עם נציג" + דירוג והמלצות (סעיף 10).

כללי היסוד של המערך — אין חריגות

  1. אין PNG יתום. כל צילום נוצר ממתכון JSON שניתן להריץ מחדש. תמונה בלי מתכון לא נכנסת לריפו.
  2. אין פרסום בלי אימות. מאמר עם verified: null לא נבנה לאתר הציבורי.
  3. אין דאטה מומצא. עובדות רק ממקור מאומת; אי-ודאות מסומנת <!-- לאימות --> ונפתרת לפני פרסום. תוקן בעקבות תקרית הסליקה (ר' סעיף 08).
  4. אין דאטה אישי בצילומים. שמות/מיילים של תלמידים מטושטשים ב-mask ברמת המתכון.
  5. אין פרסום אוטומטי של שינוי מהותי. הסוכן מכין טיוטות; אלון מאשר; רק אז דיפלוי.

סטטוס נוכחי: כל הצילומים באתר הם צילומי ביניים מהעיצובים המאושרים (מסכים מחודשים) — לא מהפרודקשיין. לפני פרסום ראשון, הסוכן מריץ capture.js מול המערכת החיה ודורס את כולם בצילומים אמיתיים (אותם שמות קבצים). הפערים הידועים מרוכזים בסעיף 08.

01עקרון הליבה — מתכוני צילום

הבעיה הקבועה של מערכי ידע היא התיישנות שקטה: המערכת משתנה ועשרות צילומים הופכים שקריים בלי שאיש יודע אילו. הפתרון — כל תמונה היא תוצר בילד, לא קובץ סטטי.

תוצאת הרצת מתכוןמשמעותטיפול
OKהמסך לא השתנה (hash זהה)כלום
CHANGEDפיקסלים השתנו — עדכון UIקוסמטי → אישור צילום · פונקציונלי → עדכון מאמר
BROKENסלקטור/ניווט נכשל — פיצ'ר הוזז או שונהחקירה בפרודקשיין, תיקון מתכון + מאמר
UNCOVEREDעמוד בפרודקשיין ללא מתכון (מזוהה ב-crawl)טיוטת מאמר + מתכונים חדשים

כך תיקיית recipes/ היא ספציפיקציה חיה של המערכת, ושאלת "מה השתנה החודש?" הופכת לשאילתת diff.

02ארכיטקטורה

אין שרת ואין DB: כל המצב חי בריפו כקבצי JSON/Markdown — גרסאות מלאות בגיט, code review על תוכן, rollback חינם.

// whiteboard-help/ — מבנה הריפו
content/categories.json      ← מקור אמת יחיד לעץ (18 קטגוריות / 82 מאמרים)
content/{teacher,student}/<cat>/<slug>.md
content/STYLE.md             ← חוקי כתיבה מחייבים לכל כותב (אנושי או סוכן)
recipes/<id>.json            ← מתכון לכל צילום (180)
recipes/baseline.lock.json   ← חתימת sha256 של כל צילום מאושר
assets/screenshots/          ← תוצרי בילד — לא נערכים ידנית
assets/{brand,img}/          ← לוגו, מסקוטים, תמונות ידניות (make-scenario)
engine/                      ← build · capture · capture-design · crawl · launch-chrome
dist/                        ← האתר הבנוי → Vercel

צד הצילום

Playwright (playwright-core) מתחבר ב-connectOverCDP לכרום ייעודי (npm run chrome, פרופיל שמור, פורט 9222) — יורש סשן מחובר לפרודקשיין. אותו דפוס שהוכח ב-Walk Me.

צד האתר

בילד Node טהור (marked בלבד, ללא framework) מרנדר HTML עצמאי: עמודי בית/קטגוריה/מאמר, אינדקס חיפוש, אזור תלמיד מבודד. פריסה: Vercel + דומיין help.whiteboard.education.

03זרימת העדכון האוטומטי

ממומש כסקיל whiteboard-kb-update (ריצה שבועית או ידנית). דורש כרום מחובר — רץ מקומית.

עדכון צילום זהה-פונקציונלית (rebrand קוסמטי) מותר אוטומטית אחרי אישור התקציר; מאמר חדש או שינוי זרימה — לעולם לא בלי אישור.

04מודל הנתונים

Frontmatter של מאמר

---
title: יצירת קורס חדש       # זהה ל-categories.json
slug: create-course
category: courses · audience: teacher | student · order: 1
description: משפט אחד — חיפוש + כותרת משנה + תשובת בורדי
verified: null              # תאריך אימות מול פרודקשיין; null = לא מתפרסם
plan: null | teacher | educator | leader | enterprise  # תג מסלול אוטומטי
related: [chapters-structure, upload-video]
---

מתכון צילום

{
  "id": "course-create-button",
  "title": "כפתור יצירת קורס בלוח הבקרה",        // alt + כיתוב
  "url": "/dashboard",                              // מאומת ב-crawl
  "themes": ["light", "dark"],
  "steps": [{ "action": "click", "selector": ".courses-tab", "settle": 300 }],
  "capture": { "type": "element | viewport | clip", "selector": "...", "padding": 24 },
  "mask": [".student-name"],                        // פרטיות — חובה על דאטה אישי
  "annotate": [{ "selector": "...", "type": "ring" }],
  "selectorSource": "approved-design",              // עד אימות מול DOM אמיתי
  "designSource": "/…/מסכים מחודשים/קורס/הגדרות קורס.html"  // מקור צילום הביניים
}

baseline.lock.json — חוזה המצב המאושר: { "<id>.<theme>": { hash, capturedAt, url } }. כל סטייה מדווחת בהרצה הבאה.

06רכיבי UI

ניווט

סיידבר ימני — אקורדיון יחיד (קטגוריה אחת פתוחה) עם אנימציית grid-rows ושברון מסתובב · TOC שמאלי "בעמוד הזה" עם עוגני h2 + scrollspy (כמו מסכי ההגדרות במערכת) · פירורי לחם · הקודם/הבא.

מאמר

תג טיוטה (עד verified) · תג מסלול ("זמין ממסלול מנהיג ומעלה") · צילומים עם lightbox והחלפת light/dark · קאלאאוטים tip/warning/info · "העתק קישור" · משוב "המדריך עזר?" עם בורדי.

חיפוש

אינדקס JSON בבילד (כותרת ×10 · ראשי פרקים ×5 · תיאור ×4 · גוף ×1), קיצור /, ניווט מקלדת. משמש גם את בורדי.

אזור תלמיד

/student/ מבודד לחלוטין: אפס קישורים לאזור המרצה, טופבר נקי, מאמרי יסוד (התחברות, איפוס סיסמה, גישה מהירה, פתקים, חוברת קורס, בורדי). המרצה משתף בכפתור "העתק קישור".

07צ'אט בורדי

בורדי נוכח בכל מסך — הירו, משוב, ו-launcher צף. הצ'אט בשפת העיצוב של דף הבית (בועות 4/16px, נקודות הקלדה, צ'יפים).

  • מנוע תשובות: retrieval קליינט-סייד על אינדקס החיפוש; עדיפות ×1.5 לקהל הנוכחי (מרצה/תלמיד); התשובה = description + תג מסלול אם רלוונטי + עד 2 חלופות.
  • השתלטות: "קח אותי לשם" → overlay עם בורדי → ניווט → פעימת הדגשה על כותרת היעד + המשך שיחה ("הגענו! זה המדריך").
  • שלב 2 (עתידי): החלפת ה-retrieval ב-API של בורדי האמיתי (RAG על אותם קובצי MD — המבנה כבר תואם), ואז ההשתלטות תוכל להצביע על שלב ספציפי במאמר.

08רישום פערים ← פרודקשיין

מרשם מחייב: כל פער בין צילומי הביניים (מהעיצובים) לבין הפרודקשיין, שחייב להיסגר לפני פרסום. הסוכן שואב את התמונות האמיתיות מהפרודקשיין לפני הפרסום הראשון — הטבלה הזו היא הצ'ק-ליסט שלו.

גורף: כל 180 הצילומים כרגע ממקור עיצוב (Monday/לוקאלי). פערים אופייניים בעיצובים: לוגו placeholder במקום הלוגו האמיתי, היעדר בורדי במסכים, דאטה דמו. אף צילום ביניים לא עולה לפרודקשיין — שער ה-verified אוכף זאת.

דגשים ליישום — דחיפת מה שלא מדויק

10פנייה לנציג + תמיכה

היציאה היחידה של מרכז העזרה אל בן-אדם: טופס "דברו עם נציג" שמזהה אוטומטית אם הפונה מרצה או תלמיד, ממלא את פרטיו אם הוא מחובר למערכת, מצרף את ההקשר (המדריך שממנו פנה, דפדפן) — ומזין את מסך ניהול הפניות ב-Admin CRM, עם מייל התראה לתיבת התמיכה ומייל אישור אוטומטי לפונה.

הזרימה מקצה לקצה

טופס באתר (סטטי) ← POST /api/support/tickets ← ולידציה + anti-spam ← שורת support_tickets ← שני מיילים במקביל: התראה לתיבת התמיכה (Reply-To = הפונה) + אישור לפונה עם מספר הפנייה ← הפנייה מופיעה במסך "שירות (CS) › ניהול פניות" במרכז הבקרה ← נציג עונה מהמסך והתשובה נשלחת לפונה במייל.

צד האתר — מה כבר בנוי (חי בבילד)

יכולתאיך זה עובד
נקודות כניסהכרטיס "דברו עם נציג" בדף הבית · כפתור בפוטר של כל עמוד · צ'אט בורדי — צ'יפ קבוע בפתיחה, "השאירו פרטים לנציג" כשאין תשובה ו"זה לא זה" אחרי כל תשובה (השאלה נכנסת לטופס) · משוב "המדריך עזר? לא" — נפתח טופס הפנייה ישירות עם שם המדריך
זיהוי קהלאוטומטי בלבד מ-data-audience של העמוד שממנו פונים (עמודי /student/ = תלמיד) — אין בחירה ידנית; מוצג לפונה "זוהה אוטומטית לפי העמוד"

מילוי אוטומטי לפונה מחוברשרשרת: window.WB_USER (כשהמרכז מוטמע במערכת) ← localStorage["wb-user"] ← GET /api/me עם credentials. שדות שמולאו מסומנים בירוק + הודעה "מולא אוטומטית — אפשר לתקן"
הקשר אוטומטינשלח עם הפנייה בלי מאמץ מהפונה: URL + כותרת המדריך הנוכחי (מוצג לפונה בשקיפות — "מצורף אוטומטית"), userAgent, ערכת נושא
שדותשם, אימייל (חובה), טלפון, נושא (תקלה טכנית / שאלה על שימוש / חיוב ותשלומים / בקשת פיצ'ר / אחר), תיאור חופשי עם placeholder מנחה ("מה ניסיתם לעשות ומה קרה בפועל")

מודל הנתונים

-- טבלת הפניות — נכנסת לסכמת המוצר לצד ה-CRM הקיים
CREATE TABLE support_tickets (
  id            TEXT PRIMARY KEY,        -- "WB-1042" — רץ, קריא ללקוח
  status        TEXT NOT NULL DEFAULT 'new',  -- new | in_progress | waiting_customer | resolved
  source        TEXT NOT NULL,           -- help-center | boardi-chat | manual
  audience      TEXT NOT NULL,           -- teacher | student
  category      TEXT NOT NULL,           -- bug | usage | billing | feature | other
  priority      TEXT NOT NULL DEFAULT 'normal',
  name          TEXT NOT NULL,
  email         TEXT NOT NULL,
  phone         TEXT,
  message       TEXT NOT NULL,
  context_url   TEXT,                    -- המדריך שממנו נשלחה הפנייה
  context_title TEXT,
  user_agent    TEXT,
  user_id       TEXT REFERENCES users(id), -- אם הפונה זוהה כמחובר — קישור ל-CRM
  assignee_id   TEXT REFERENCES admins(id),
  created_at    TIMESTAMPTZ NOT NULL DEFAULT now(),
  first_response_at TIMESTAMPTZ,         -- מדד SLA
  resolved_at   TIMESTAMPTZ
);
-- הודעות בפנייה (תשובות נציג במייל + הערות פנימיות)
CREATE TABLE support_ticket_messages (
  id         TEXT PRIMARY KEY,
  ticket_id  TEXT NOT NULL REFERENCES support_tickets(id),
  author     TEXT NOT NULL,               -- customer | agent | system
  body       TEXT NOT NULL,
  internal   BOOLEAN NOT NULL DEFAULT false, -- הערה פנימית — לא נשלחת לפונה
  created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

חיבור ל-Admin CRM

  • מסך ניהול ייעודי: "שירות (CS) › ניהול פניות" במרכז הבקרה — KPI (פתוחות, זמן תגובה ראשונה, SLA בסיכון, נפתרו השבוע), טאבים לפי סטטוס, סינון לפי קהל/נושא/מקור/אחראי, מגירת פנייה עם ציר זמן, תשובה במייל מהמסך, הערות פנימיות, ו"העבר למוצר ובאגים" לאסקלציה. עוצב על מערכת העיצוב של מסכי ההנהלה הקיימים.
  • קישור ל-CRM אנשי קשר: פנייה מפונה מזוהה (user_id) מופיעה גם בכרטיס איש הקשר — ההיסטוריה השירותית ליד ההיסטוריה העסקית.
  • זרימת סטטוסים: חדש ← בטיפול (תשובה ראשונה — עוצר SLA) ← ממתין ללקוח ← נפתר. פנייה בקטגוריית "תקלה טכנית" שמאומתת כבאג — מועברת למסך "מוצר ובאגים" עם קישור דו-כיווני.
