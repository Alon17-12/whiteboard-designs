מדריך יישום · CTO

מערכת דיוור — עורך מייל מבוסס בלוקים

פלואו יצירת המייל (מיושר 2026-07-29): נמענים → עורך → שליחה. שלב 1 — בחירת רשימות (עם ניכוי-כפילויות חי). שלב 2 — עורך בלוקים inline שכולל בראשו נושא + Preheader (מסך הפתיחה הנפרד בוטל — הנושא/preheader עברו לראש העורך) ורצועת "נשלח אל". שלב 3 — מודל שליחה (סיכום נמענים + תזמון: שלח עכשיו / תזמן לתאריך). העורך = בדיוק אותו מודל בלוקים של הקורס: "הוסף בלוק תוכן" → block‑picker → בלוק inline נערך במקום. אותו addBlock(), אותם .content-block. סדרות מיילים מוגדרות בדף נפרד.

00סקירה + כללי CTO

העורך משרת שלושה סוגים: קמפיין בודד, שלב בסדרת drip, ומייל מבוסס‑טריגר — כולם משתמשים באותו עורך ובאותו מודל בלוקים.

5 כללי הזהב (חובה)

  1. React + Next.js — העורך הוא Client Component (אינטראקטיבי); הרשימות/הגדרות כ‑Server Components.
  2. TypeScript strict + Zod — סכמת הבלוקים מאומתת ב‑Zod (אותה סכמה בקורס ובמייל).
  3. Bunny CDN/Stream — תמונות הבלוקים ווידאו דרך Bunny; אין העלאות לשרת.
  4. Trigger.dev — כל שליחה, סדרה והשהיה — דרך Trigger.dev (בלי cron/setTimeout).
  5. Toast/Modal מעוצבים — אין alert/confirm; שמירה אוטומטית + טוסט.

01מה תוקן ב‑UX

לפני

  • פופאפ הגדרות ואז קפיצה לעורך נפרד
  • 5 טאבים תוכן (AI / HTML / ויזואלי / תצוגה / עורך HTML) — בלבול
  • אין באמת בונה‑בלוקים
  • אין ייצוג לסדרת מיילים / השהיות
  • סטטוסים לא ברורים (פעיל/מתוזמן/מתמשך)

אחרי

  • פלואו נקי בן 3 שלבים: נמענים → עורך → שליחה (נושא+Preheader בראש העורך)
  • בחירה מפורשת: עורך ויזואלי או בניית HTML
  • עורך בלוקים inline זהה לקורס — "הוסף בלוק" → block‑picker
  • עריכה במקום, toolbar מינימלי (מעלה/מטה/מחק) — בלי הגדרות מיותרות
  • סדרות מוגדרות בדף נפרד (לא בתוך העורך)
  • CTA ראשי יחיד (שמור) + שלח טסט + תצוגה מקדימה

עקרון מנחה (UI/UX Pro Max): פשוט ונקי — ברירות מחדל חזקות, מעט מאוד הגדרות לכל בלוק. עריכה inline (contenteditable) במקום פאנל מאפיינים. משתנים אישיים מוצגים בעברית (מה הם אומרים) ומוכנסים כטוקן.

03מודל הבלוקים המשותף

הלב של האיחוד: גוף המייל וגוף שיעור בקורס הם אותו מבנה — מערך בלוקים מסודר. רג'יסטרי אחד מגדיר כל סוג בלוק; הקשר (קורס/מייל) רק מסנן אילו בלוקים זמינים ואיך הם מרונדרים.

// lib/blocks/registry.ts — מקור אמת אחד
// בלוקי התוכן המשותפים עם הקורס — אותם labels/אייקונים
type SharedBlock =
  "h1" | "h2" | "text" | "quote"
  | "divider" | "cta" | "image";
// "iframe" קיים בקורס אך מוסר במייל — לא נתמך בלקוחות דוא"ל (Gmail/Outlook)
// תוספות ייעודיות-מייל שנכנסות לאותו picker:
type EmailBlock = SharedBlock
  | "spacer" | "social"          // מרווח (S/M/L) · רשתות חברתיות
  | "signature" | "product"      // חתימה אישית · כרטיס קורס/מוצר
  | "imgtext" | "copybox"        // תמונה+טקסט זה-לצד-זה · תיבת העתקה/קופון
  | "gallery" | "countdown"      // גלריית תמונות · ספירה לאחור (נרנדר כ-GIF בשרת)
  | "addr"                       // פוטר כתובת ופרטי קשר (משלים את unsub חוקית)
  | "unsub";  // הסרה מרשימת התפוצה — נוסף כברירת מחדל, חובה, לא נמחק

interface BlockDef<P> {
  type: BlockType;
  contexts: ("course" | "email")[];   // היכן זמין
  schema: ZodSchema<P>;                  // ולידציית props
  defaults: P;
  Editor: FC<{props:P; onChange:(p:P)=>void}>;  // תצוגה בקנבס
  Props:  FC<{props:P; onChange:(p:P)=>void}>;  // פאנל מאפיינים
  renderEmail?: (props:P, ctx:RenderCtx) => string; // HTML תואם-מייל
}

// גוף המסמך (מייל או שיעור) — אותו טיפוס
type BlockDoc = { id:string; type:BlockType; props:unknown }[];

תוצאה: שיפור בבלוק (נגישות, עיצוב) מגיע בו‑זמנית לקורס ולמייל. תוספת בלוק = רישום אחד ב‑registry.

04רינדור למייל + משתנים

בקנבס הבלוקים מרונדרים כ‑React (תצוגה חיה). לשליחה הם מתקמפלים ל‑HTML תואם‑מייל (טבלאות + CSS inline) — לקוחות מייל לא תומכים ב‑flex/grid. מומלץ MJML או רנדרר טבלאי פנימי.

רספונסיביות (חובה): המייל חייב להיראות תקין במובייל ובדסקטופ. רינדור מבוסס‑טבלאות עם רוחב נוזלי ו‑media queries מוטמעים; תמונה+טקסט וכרטיס קורס קורסים לעמודה אחת במובייל, שורת הרשתות עוטפת (wrap), והטיימר/גלריה מצטמצמים. העורך כולל מתג מחשב/נייד בתצוגה המקדימה לאימות.

הצעת שמירה חכמה (לחידוד): כשמרצה מסיים להגדיר בלוק אישי/חוזר (חתימה, רשתות, פוטר, CTA, קופון) — מוצעת שמירה ל"הבלוקים שלי". טריגר נכון: רק אחרי עריכה ממשית (input) + יציאת פוקוס, פעם אחת לכל בלוק; לא נורה אחרי מחיקה או על פעולות לא רלוונטיות (כמו בחירת קורס). שדרוג עתידי: לשקלל "אינדיקציית חשיבות" (אורך תוכן, מילוי קישורים, שימוש חוזר) לפני ההצעה.

// בעת שליחה לכל נמען — אינטרפולציה של משתנים
function compile(doc: BlockDoc, recipient: Recipient): string {
  const html = doc.map(b => registry[b.type].renderEmail!(b.props, ctx)).join("");
  return interpolate(html, {
    member_name: recipient.name,
    club_name:   ctx.club.name,
    login_url:   signedLoginLink(recipient),   // קישור חתום פר נמען
    club_slug:   ctx.club.slug,
  });
}
// {{member_name}} → "מיכל" ; חסר ערך → fallback מוגדר

תאימות מייל: CSS inline, רוחב ≤600px, טבלאות לפריסה, alt לכל תמונה, ו‑fallback לכל משתנה. בלוקים כמו columns מתקמפלים לטבלה, לא ל‑flex.

AIבורדי כקופירייטר מכירות + רפרנס סגנון

בורדי הוא לא "מנסח טקסט" גנרי — הוא task-BOARDi מיומן בכתיבת קופי מכירות לקורסים דיגיטליים (יוצר הדיוור, ראה סקיל boardi-builder). כל טיוטה מוזנת משני עוגנים: (1) מתודולוגיית קופי מובנית במערכת-הפרומפט; (2) רפרנס אישי לקול ולסגנון של המרצה. ככל שיש יותר רפרנס — הפלט נשמע יותר "המרצה", פחות גנרי.

עוגן 1 · מערכת-הפרומפט (הקופירייטר)

ה-system prompt מגדיר את בורדי כקופירייטר Direct-Response לקורסים דיגיטליים, עם ארגז-כלים של מסגרות מוכחות. חשוב: אלה מתודולוגיות שנלמדות, לא חיקוי אישיות/מותג של אף אדם.

מסגרות מובנות (מתודולוגיה)

  • Alex Hormozi — Value Equation: להגדיל את התוצאה-הנחשקת ואת סבירות-ההצלחה הנתפסת, להקטין זמן ומאמץ; offer-stacking.
  • Russell Brunson — Hook · Story · Offer + Value Ladder + epiphany bridge.
  • עידן וולר — direct-response עברי: שפת דיבור, פתיח שעוצר גלילה, P.S. אפקטיבי.
  • קלאסי: PAS · AIDA · 4U לכותרת הנושא.

Guardrails (חובה)

  • ללא הבטחות שווא / הכנסה מובטחת (ציות + מוניטין שולח).
  • CTA יחיד וברור לכל מייל.
  • נושא ≤ ~45 תווים · preheader משלים, לא חוזר על הנושא.
  • טון · אורך · אימוג'י לפי ה-VoiceProfile של המרצה, לא ברירת-מחדל.
  • עברית טבעית, RTL, בלי "תרגומית".

עוגן 2 · שני מקורות רפרנס-הסגנון

מקוראיך נאסףלמה משמש
דוגמאות שהמרצה מעלהבורדי מבקש דוגמה לקופי (שלו/השראה) בפלואו. ask-and-proceed: אם אין — ממשיך בלי לחסום. העלאה / הדבקה / URL → CopyReference.טון וקצב מועדפים, ניסוחים אהובים.
ארכיון מיילים שנשלחו (אוטומטי)כל מייל שיצא — מצ'אט בורדי ומקהילת המייל — נשמר: טקסט, מבנה בלוקים (doc), עיצוב/מותג ומדדי פתיחה/קליק → SentEmailArchive.מבנה ויזואלי, שפה, ומה עובד אצל הקהל (משקל לפי ביצועים).

בקשת הרפרנס בפלואו: אחרי שלב הטון, בורדי מציג כרטיס "לומד לכתוב בקול שלך" — מציין שכבר למד מ-N מיילים קודמים, ומציע להעלות דוגמה. שני מסלולים: "העלה דוגמה" או "אין לי — למד מהמיילים שלי". תמיד מתקדם, לעולם לא חוסם על היעדר רפרנס.

לולאת שיפור: מיילים עם פתיחה/קליק גבוהים מקבלים משקל גבוה יותר כרפרנס — כך בורדi לומד לא רק את הקול של המרצה, אלא מה ממיר אצל הקהל שלו. פרטיות: כל האינדוקס מסונן teacherId (RLS); רפרנס של מרצה אחד לעולם לא זולג לאחר.

מודלים (Prisma) · רפרנס-סגנון

model CopyReference {        // דוגמאות קופי שהמרצה העלה (אופציונלי)
  id        String @id @default(cuid())
  teacherId String
  source    String            // upload | paste | url
  title     String?
  body      String            // הטקסט הגולמי
  notes     String?           // "אהבתי את הפתיח"
  embedding Unsupported("vector")?  // pgvector
  createdAt DateTime @default(now())
}

model SentEmailArchive {     // כל מייל שנשלח — רפרנס אוטומטי
  id         String @id @default(cuid())
  teacherId  String
  campaignId String?          // אם נשלח מהמערכת
  origin     String           // boardi_chat | mail_community | manual
  subject    String
  preheader  String?
  doc        Json             // BlockDoc — המבנה הוויזואלי
  html       String           // הרינדור הסופי
  openRate   Float?           // משקל רפרנס
  clickRate  Float?
  embedding  Unsupported("vector")?
  sentAt     DateTime
}

model VoiceProfile {         // פרופיל-קול נגזר, אחד למרצה
  teacherId   String @id
  tone        String          // "חם/אישי" | "תכליתי" ...
  traits      Json            // אורך משפט, אימוג'י, ביטויים, מבני CTA מועדפים
  sampleCount Int             // כמה מיילים/דוגמאות מאחורי הפרופיל
  updatedAt   DateTime @updatedAt
}

Action-API / tools: upsert_copy_reference (העלאה), search_copy_reference(goal,k) ו-get_voice_profile(teacherId) (קריאה, מזינים את הקשר-הכתיבה), ו-index-sent-email שנורה אוטומטית ב-send-campaign. הכתיבה עצמה נשארת preview→confirm ככל פעולת בורדי.

05מודל הנתונים (Prisma)

בינדינג אוטומטי לדאטה (חובה): בלוקים שמושכים נתונים אמיתיים מתמלאים אוטומטית מהמערכת — פרופיל המרצה (חתימה: שם/תפקיד/אווטאר/קישורים), הדר/מיתוג (לוגו, צבע מותג, שם המועדון), וכרטיס קורס (בחירת קורס מתוך הקטלוג → שם/תמונה/מחיר נטענים אוטומטית). בלוקי תמונה פותחים בורר מתוך ספריית המדיה של המשתמש. ה‑UI: כל אזור תמונה → <MediaPicker>; כרטיס קורס → <CoursePicker> (Server Component שמושך מ‑Course / LecturerProfile / BrandKit). בזמן שליחה הערכים מוקפאים ל‑snapshot כדי שמיילים ישנים לא ישתנו.

model EmailTemplate {
  id        String  @id @default(cuid())
  name      String          // שם פנימי
  subject   String
  preheader String?
  fromName  String
  doc       Json            // BlockDoc — מערך הבלוקים
  brand     Json            // רקע, צבע מותג, גופן, רוחב
  attachmentId String?
  contextType  String       // club | course | school
  contextId    String
  createdAt DateTime @default(now())
  updatedAt DateTime @updatedAt
}

model Campaign {       // קמפיין בודד
  id         String @id @default(cuid())
  templateId String
  audience   Json           // everyone | leads | customers | tag:... | filter
  sendMode   SendMode       // NOW | SCHEDULED
  scheduledAt DateTime?
  status     CampaignStatus // DRAFT | SCHEDULED | SENDING | SENT
  stats      Json?          // נשלח/נפתח/קליקים
}

model EmailSeries {    // סדרת drip
  id      String @id @default(cuid())
  name    String
  trigger TriggerType?   // JOIN | CART_ABANDON | COMPLETE | INACTIVE | null(ידני)
  steps   EmailStep[]
  active  Boolean @default(false)
}
model EmailStep {
  id         String @id @default(cuid())
  seriesId   String
  templateId String
  order      Int
  delayHours Int            // השהיה לפני שלב זה
  condition  Json?          // אופציונלי: רק אם לא נפתח וכו'
}

06קמפיין · סדרה · טריגר

סוגמודלשליחה
קמפיין בודדCampaign → EmailTemplateמיידי או מתוזמן, לכל הקהל/מסונן.
סדרת dripEmailSeries → EmailStep[]שלב‑אחר‑שלב עם delayHours בין שלבים.

שלושתם חולקים את EmailTemplate (אותו עורך). בחירת סוג הדיוור בבורדי ממפה ישירות: "מייל בודד מתוזמן" → Campaign (sendMode = NOW | SCHEDULED + scheduledAt); "סדרת מיילים קבועה" → EmailSeries (ידני או trigger).

קהל דינמי · פילוח לפי התנהגות

קהל היעד הוא לא רשימה סטטית אלא שאילתה חיה על ה-Metrics Layer. בורדי בונה אותה משפה חופשית או מבונה-הפילוח, והיא מתעדכנת לבד עד לשליחה. הבסיס תומך: כולם · לידים · לקוחות · מיובאים · תגית · רשימה. מעליו — סגמנטים התנהגותיים (auto-lists שהמערכת מזהה לבד):

// audience — נשמר ב-Campaign.audience / EmailSeries; מתקמפל ל-live query
audience = {
  base: "all" | "leads" | "customers" | "list:<id>" | "course:<id>:students",
  behavior?: [                                // אפס או יותר תנאים התנהגותיים
    { type: "inactive_days", course: "<id>" | "all", gte: 14 },  // לא נכנסו ≥ N ימים (לקורס / לכל הקורסים)
    { type: "joined", op: "after" | "before", date: "2026-06-01" }, // הצטרפו לפני/אחרי תאריך
    { type: "cart_abandon", course: "<id>" }               // נוטשי עגלה של קורס
  ],
  dedup: true                                  // תמיד — union ייחודי, נמען מקבל מייל אחד
}
// resolveAudience(audience) → Recipient[] ; ריצה על ה-Metrics Layer (Tier-1 native), RLS לפי teacherId
// הספירה בבורדי + במסך בחירת-הרשימות = |union|, לעולם לא סכום (ראה מסך "מייל חדש - בחירת רשימות")

סגמנטים דינמיים כרשימות אוטומטיות: inactive_days / cart_abandon / course:students מוצגים למרצה כרשימות אוטומטיות (תג "אוטומטי"/"סגמנט דינמי") — אי אפשר לערוך ידנית, המערכת מתחזקת. זהו היסוד שה-AI יושב מעליו: בורדי בוחר/מרכיב סגמנטים, וההלימה (dedup) מובטחת תמיד. joined-before/after-date ו-inactive_days משתנים = פרמטרים חיים של אותו סגמנט.

// trigger/mailing/enroll-series.ts
export const enrollSeries = task({
  id: "enroll-series",
  run: async ({ seriesId, userId }) => {
    const steps = await getSteps(seriesId);
    let delay = 0;
    for (const s of steps) {
      delay += s.delayHours;
      await runSeriesStep.trigger({ stepId: s.id, userId }, { delay: `${delay}h` });
    }
  },
});

  • .block-toolbar — מעלה/מטה/מחק בלבד

  • עריכה contenteditable במקום — ללא PropertiesPanel

בית הדיוור (סקירה)

  • 4 KPI: נמענים פעילים (|union| חי) · מיילים שנשלחו (30 יום) · פתיחה ממוצעת · לחיצה ממוצעת
  • <RecentEmails> — מיילים אחרונים חוצי‑רשימות + סטטיסטיקת פתיחה/קליק לכל מייל
  • <MyLists> — 7 רשימות (ידניות/אוטומטיות) · מקור‑אמת אחד המשותף לכל מסכי הדיוור
  • ניווט‑צד פעיל = "רשימות תפוצה"; דיוור = סקשן (בית הדיוור ↔ רשימות)

<ActivityChart> — גרף פעילות

  • עמודים מקובצים (grouped, לא stacked): לכל שבוע שני עמודים — פתיחה (cyan) לצד קליק (green)
  • תווית ערך מעל כל עמוד בצבע התואם ללגנדה — הגרף לא קריא בלי המספרים
  • סקאלה אחת משותפת לשני המדדים (F px לאחוז) — היחס בין הברים נשמר ביושר; אין להערים מדדים בסקאלות שונות
  • כיתוב‑משנה מסביר את היחידה ("שיעור פתיחה/קליק מתוך הנמענים"); קו‑בסיס תחתון; סדר RTL (העדכני מימין)
  • מקור נתונים: aggregation של open/click אירועי מייל לכל חלון שבועי

נגישות: הוספה בלחיצה מה‑block‑picker (לא תלוי גרירה), הזזה דרך toolbar (מעלה/מטה), aria-labels על כל כפתורי הבלוק, focus עובר אוטומטית לבלוק החדש, ו‑prefers-reduced-motion לאנימציות.
